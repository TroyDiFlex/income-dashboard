# Подготовка миграции в Turso

Это первый этап, без переключения рабочего приложения. Существующий интерфейс и API продолжают использовать Google Таблицу. Новых npm-зависимостей нет; для локальной проверки SQLite нужен Node.js 22.16 или новее.

## Сохранность данных

- Резервные копии Apps Script сохраняются бессрочно по умолчанию. Возврат к старой очистке возможен только явной серверной настройкой `BACKUP_CLEANUP_ENABLED=true`.
- Папка архива перед миграцией должна отличаться от `BACKUP_FOLDER_ID`: старое развёртывание не должно иметь причины очищать защищённый архив.
- Исходная таблица и старые файлы остаются на месте. Проверка восстановления использует только отдельную SQLite-базу в памяти.
- `scripts/verify-archive.mjs` проверяет контрольную сумму каждого JSON и восстанавливает его источники, все суммы в копейках, нули, отсутствие записей и исходные даты корзины. Проверяется полное содержимое, а не только общая сумма.
- Необратимые операции, создание учётных записей и отправка писем не выполняются этой проверкой.

```sh
node scripts/verify-archive.mjs .local/migration-2026-10-17/archive
```

Архив и отчёт должны оставаться в `.local/`, исключённой из Git. Финансовые данные, токены, почта владельца и идентификаторы закрытых файлов не должны попадать в публичный репозиторий.

## Перенос данных

В `.local/turso.env` нужны `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` с доступом только к целевой базе. Токен читает локальный процесс; интерфейс его не получает. Соединения допускаются только по HTTPS с доменом базы Turso. Перенаправления запрещены.

```sh
node scripts/migrate-turso.mjs --check
node scripts/migrate-turso.mjs --import .local/migration-2026-10-17/archive/potok-backup-TIMESTAMP.json
```

Импорт создаёт отдельный постоянный ID профиля в состоянии `pending_owner`. Он не привязывается к первому зарегистрировавшемуся пользователю. Привязка владельца потребует отдельного проверенного входа и административной операции.

Каждый импорт выполняется в одной транзакции. При ошибке более поздние шаги пропускаются, вместо COMMIT выполняется ROLLBACK. Повторный запуск с тем же файлом проверяет результат и не дублирует записи. Другие данные в том же целевом профиле импорт не перезаписывает. После сетевого обрыва повторный запуск сначала проверяет сохранённый результат.

Полный исходный JSON сохраняется в `potok_imports` вместе с контрольной суммой. Это сохраняет исторический порядок, метаданные и корзину независимо от нормализованных таблиц. Таблицы источников и доходов имеют составные ключи с ID владельца: одинаковые ID источников в двух профилях не смешивают данные.

## Подготовленные модули входа

`backend/credentials.mjs` хеширует отдельные пароли приложения через scrypt со случайной солью. Для логина почта не нужна. `backend/google-identity.mjs` проверяет подпись Google локально по публичным ключам, адресата, издателя, срок и nonce. Почта служит только метаданными; идентификатор Google определяется парой issuer + subject.

Эти модули ещё не образуют готовый сервис авторизации. Перед включением обязательны:

1. Серверные обработчики регистрации, входа, привязки и замены способов входа.
2. Одноразовое серверное хранение и погашение Google nonce, защита от CSRF, ограничения частоты попыток.
3. Сеансы с серверным отзывом, проверка владельца на каждом запросе и в транзакции изменения.
4. Подтверждение резервной почты, одноразовые ограниченные по времени токены восстановления, повторная проверка личности перед сменой пароля или привязок.
5. Коды восстановления для профилей без почты; сохранение хотя бы одного рабочего способа входа.
6. Выбор и настройка серверного размещения и отправителя писем. Данные Turso сами по себе не предоставляют эти возможности.

Пароль Google приложение не получает. Отдельный пароль «Потока» пользователь задаёт сам. Потеря доступа к Google решается только заранее привязанным способом или кодами восстановления. Смена привязки сохраняет постоянный ID профиля и доходы. Совпадение email не является основанием объединять профили.

## Подготовка офлайн-работы

`offline-store.js` содержит хранилище IndexedDB: снимок и очередь сохраняются в одной транзакции отдельно для каждого профиля. Порядок изменений присваивается внутри транзакции. `offline-sync.js` содержит проверяемый без браузера механизм согласования.

- При возобновлении связи проверяется сеанс, затем актуальные данные. Каждый запрос API обязан дополнительно проверять ожидаемый ID профиля.
- При отзыве сеанса или смене профиля очередь сохраняется и не отправляется в другой профиль.
- Потеря ответа после записи не удаляет локальное изменение. Повторная сверка узнаёт уже применённые значения.
- Разные месяцы и независимые поля источника объединяются. Разные версии одной суммы не складываются.
- Удалённый на сервере источник не восстанавливается автоматически.
- Выбор пользователя применяется только к показанному изменению и версии сервера. Если сервер снова изменился, требуется новая сверка.

В рабочий интерфейс эти модули пока не подключены. Нужны service worker для файлов приложения, индикация состояния, экран разрешения конфликтов, интеграция с реальными профилями и сеансами и проверка IndexedDB на целевых устройствах. Установка приложения сейчас по-прежнему не гарантирует офлайн-работу. Локальное хранилище может быть очищено пользователем или системой и не заменяет резервные копии.

## Условия переключения

Подтверждён владелец; проверены Google и отдельный вход, восстановление, перепривязка, изоляция двух профилей, отзыв сеансов, потеря сети, повторная доставка и конфликты. Сделана свежая полная копия живого API, включая свойства корзины: копия самой таблицы не содержит этих свойств. Повторно сверены все данные и архив. Только после этого переключается рабочий интерфейс; старый источник остаётся доступен для восстановления.
